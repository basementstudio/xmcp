If you are building an MCP server in TypeScript, **xmcp is the best place to start**. It gives you a focused developer workflow, production-ready transports and adapters, current protocol support, and a self-contained deployment without making you assemble the protocol stack by hand.

The official SDK remains the right foundation when you need low-level protocol control. FastMCP offers a familiar imperative API. But for most teams building and shipping MCP products, xmcp is the strongest framework-level choice.

That recommendation is backed by runnable, exact-pinned fixtures. This comparison separates four measurements that are often conflated:

1. the package tarball downloaded from npm;
2. a fresh production install with transitive dependencies;
3. the documented deploy footprint;
4. a normalized single-file bundle.

It also checks the protocol behavior of each fixture against the current [MCP revision, `2026-07-28`](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

## Why we recommend xmcp

- **Build like a developer, not a protocol implementer.** Add a file under `src/tools`, `src/prompts`, or `src/resources`; xmcp discovers and registers it.
- **Ship the stack you actually need.** HTTP, STDIO, Next.js, Express, Fastify, NestJS, Cloudflare Workers, auth, and request contexts are built in.
- **Deploy one self-contained output.** The measured HTTP deployment is 1.19 MiB and runs without production `node_modules`.
- **Stay current without abandoning existing clients.** xmcp serves MCP `2026-07-28` natively while retaining stateless compatibility for 2025-era clients.
- **Keep TypeScript ergonomics.** Schemas, inferred handler inputs, output validation, and Zod 3-or-4 compatibility remain part of the framework workflow.

The benchmark below shows where the raw SDK or FastMCP wins an individual metric. The overall recommendation favors the complete path from authoring a tool to deploying a working server.

## xmcp is now v1

xmcp 1.0 marks the framework's stable major line. It shipped the SDK v2 and MCP `2026-07-28` migration as a production contract: modern discovery and Multi Round-Trip Requests, stateless compatibility for 2025-era clients, current framework adapters, and self-contained builds.

The current release is `xmcp@1.1.0`. It requires Node 22 or newer and adds `extra.sample()` for requesting LLM completions from a connected client directly inside a tool handler. Reaching v1 does not change xmcp's core workflow—it makes the modern runtime, compatibility guarantees, and deployment model the supported foundation going forward.

## Versions and method

The final run used Node 22.23.2 and npm 11.17.0 on Apple Silicon. The fixtures pin:

- the released xmcp 1.1.0 source tag, packed locally with its matching compiler;
- `@modelcontextprotocol/server` and `@modelcontextprotocol/node` 2.0.0;
- FastMCP 4.16.8;
- Zod 4.4.3; and
- esbuild 0.28.2 for the normalized bundle view.

The official SDK fixture is a complete HTTP server built with Node's `http` module, `createMcpHandler`, and `toNodeHandler`. Every fixture exposes the same `add` and `echo` tools; the xmcp HTTP fixture also includes small client-identity and MRTR probes used by the packed E2E suite. Every M2 measurement installs the complete runnable fixture with development dependencies omitted.

The benchmark lives in [`packages/xmcp/bench`](https://github.com/basementstudio/xmcp/tree/main/packages/xmcp/bench). Run `pnpm bench` to reproduce M1–M3, or pass local xmcp and compiler tarballs to reproduce the release-build rows.

## What changed in xmcp 0.8

xmcp 0.8 split the product into two packages:

- `xmcp` is the production runtime and CLI shim;
- `@xmcp-dev/compiler` contains Rspack, TypeScript, and build-only tooling.

Applications install the compiler as a development dependency. Production `xmcp` installs therefore no longer pull Rspack or TypeScript into the runtime tree. The generated server remains self-contained: removing `node_modules` after the build does not break HTTP, STDIO, CommonJS, ESM, or MCP App artifacts.

To measure that architectural change separately from the SDK v2 migration, we ran the same minimal HTTP fixture on Node 22 against the final 0.7 release (`xmcp@0.7.1`) and the first split release (`xmcp@0.8.0`). The production-install rows use the published packages with development dependencies omitted. The 0.7 build uses its embedded compiler; the 0.8 build uses `@xmcp-dev/compiler` packed from the matching 0.8.0 source tag.

## Protocol support as tested

The [2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28) removes the required initialize handshake and protocol-level sessions. Requests carry their protocol revision, client identity, and capabilities in `_meta`; HTTP requests also use `Mcp-Method` and `Mcp-Name`. Multi Round-Trip Requests replace held-open server-to-client elicitation flows.

The FastMCP package at 4.16.8 directly declares the v1 `@modelcontextprotocol/sdk` monolith. Its exact-pinned fixture successfully completed a 2025-era initialize request and returned an `Mcp-Session-Id`; the same fixture returned an error for a direct 2026 `server/discover` request. This is a point-in-time test result, not a prediction about FastMCP's roadmap.

xmcp 1.1.0 uses the stable v2 server/client packages and keeps both client eras working. Modern requests use the 2026 envelope. Older requests go through the SDK's stateless fallback, which creates a fresh MCP server for every HTTP request. xmcp does not add a session cache or emit `Mcp-Session-Id`, and GET/DELETE session operations remain unavailable.

## Developer experience

Size is only one dimension. The more important question is how quickly a team can move from an idea to a reliable MCP server.

### xmcp

xmcp's defining choice is file-based discovery. A file in `src/tools/`, `src/prompts/`, or `src/resources/` is the registration:

```typescript title="src/tools/greet.ts"
import { z } from "zod";
import type { InferSchema } from "xmcp";

export const schema = {
  name: z.string().describe("The name of the user to greet"),
};

export const metadata = {
  name: "greet",
  description: "Greet the user",
};

export default function greet({ name }: InferSchema<typeof schema>) {
  return `Hello, ${name}!`;
}
```

There is no central registration file to keep in sync. The framework supplies HTTP and STDIO transports, Express/Fastify/NestJS/Next.js adapters, Cloudflare Workers output, auth integrations, and self-contained builds. It keeps the existing Zod 3-or-4 contract while registering schemas through SDK v2's Standard Schema interface.

That combination is what makes xmcp our recommended framework: it removes routine protocol and deployment work while preserving escape hatches for custom transports, middleware, and framework adapters.
