There are three realistic starting points for a TypeScript MCP server: use the official SDK directly, add an imperative framework such as FastMCP, or use a file-based framework such as xmcp. They optimize for different things, so a registry tarball alone does not tell you which one is smaller—or which one is right for your project.

This comparison uses runnable, exact-pinned fixtures and separates four measurements that are often conflated:

1. the package tarball downloaded from npm;
2. a fresh production install with transitive dependencies;
3. the documented deploy footprint;
4. a normalized single-file bundle.

It also checks the protocol behavior of each fixture against the current [MCP revision, `2026-07-28`](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

## Versions and method

The final run used Node 20.20.2 and npm 11.17.0 on Apple Silicon. The fixtures pin:

- the xmcp 0.8.1 migration candidate, packed locally from the 0.8.0 code line;
- `@modelcontextprotocol/server` and `@modelcontextprotocol/node` 2.0.0;
- FastMCP 4.16.5;
- Zod 4.4.3; and
- esbuild 0.28.2 for the normalized bundle view.

The official SDK fixture is a complete HTTP server built with Node's `http` module, `createMcpHandler`, and `toNodeHandler`. Every fixture exposes the same `add` and `echo` tools; the xmcp HTTP fixture also includes small client-identity and MRTR probes used by the packed E2E suite. Every M2 measurement installs the complete runnable fixture with development dependencies omitted.

The benchmark lives in [`packages/xmcp/bench`](https://github.com/basementstudio/xmcp/tree/main/packages/xmcp/bench). Run `pnpm bench` to reproduce M1–M3, or pass local xmcp and compiler tarballs to reproduce the migration-candidate rows.

## Results

### M1: package tarball

| Fixture                       |    Tarball | Unpacked |
| ----------------------------- | ---------: | -------: |
| xmcp 0.8.1 candidate          |   1.44 MiB | 4.94 MiB |
| FastMCP 4.16.5                | 379.67 KiB | 1.64 MiB |
| Official server package 2.0.0 |   1.42 MiB | 6.01 MiB |

FastMCP wins this narrow measurement. But this is the size of one published package, not the size of a runnable application. In particular, the official row measures `@modelcontextprotocol/server`; its Node adapter and Hono peer are counted in the fresh-install and deployment views below.

### M2: fresh production install

| Fixture              | `node_modules` | Dependency entries |
| -------------------- | -------------: | -----------------: |
| xmcp 0.8.1 candidate |       9.29 MiB |                  2 |
| Official SDK v2 HTTP |      13.25 MiB |                  6 |
| FastMCP 4.16.5       |      38.93 MiB |                182 |

This is the more useful local-install comparison. xmcp's production dependency tree contains its Zod peer and the packed runtime; Rspack and TypeScript are not production dependencies. The official SDK remains compact when assembled into a runnable Node HTTP server. FastMCP provides more framework behavior, and its larger transitive graph reflects that.

One Node 20 caveat is worth recording: FastMCP installed and its legacy HTTP fixture started successfully, but npm emitted an engine warning because the resolved `pipenet@1.4.2` dependency declares Node 22 or newer.

### M3: deployment and bundle

| Fixture              | Documented deploy footprint | Normalized bundled artifact |
| -------------------- | --------------------------: | --------------------------: |
| xmcp HTTP            |                    1.19 MiB |                    1.19 MiB |
| xmcp STDIO           |                  524.71 KiB |                  524.69 KiB |
| Official SDK v2 HTTP |                   13.25 MiB |                  646.54 KiB |
| FastMCP HTTP         |                   38.93 MiB |                    1.80 MiB |

The deployment view follows each project's normal output: xmcp's generated, self-contained `dist/`, or compiled source plus production `node_modules` for the other fixtures. The bundle view instead asks esbuild to collapse each non-xmcp fixture into one minified file and compares that file with xmcp's generated transport artifact.

That distinction matters. The raw SDK produces the smallest normalized HTTP bundle, while xmcp produces the smallest ready-to-copy HTTP deployment directory. xmcp's generated output runs without `node_modules`; the benchmark smoke-tests exactly that deployment shape.

## What changed in xmcp 0.8

xmcp 0.8 split the product into two packages:

- `xmcp` is the production runtime and CLI shim;
- `@xmcp-dev/compiler` contains Rspack, TypeScript, and build-only tooling.

Applications install the compiler as a development dependency. Production `xmcp` installs therefore no longer pull Rspack or TypeScript into the runtime tree. The generated server remains self-contained: removing `node_modules` after the build does not break HTTP, STDIO, CommonJS, ESM, or MCP App artifacts.

To measure that architectural change separately from the SDK v2 migration, we ran the same minimal HTTP fixture on Node 20 against the final 0.7 release (`xmcp@0.7.1`) and the first split release (`xmcp@0.8.0`). The production-install rows use the published packages with development dependencies omitted. The 0.7 build uses its embedded compiler; the 0.8 build uses `@xmcp-dev/compiler` packed from the matching 0.8.0 source tag.

| Measure                        |   xmcp 0.7.1 |  xmcp 0.8.0 | Reduction |
| ------------------------------ | -----------: | ----------: | --------: |
| Runtime tarball                |  4,126,552 B | 2,018,611 B |    51.08% |
| Unpacked runtime package       | 12,398,118 B | 6,054,013 B |    51.17% |
| Fresh production install       |   101.12 MiB |   10.12 MiB |    89.99% |
| Production dependency entries  |          169 |           2 |    98.82% |
| Full development install       |   101.12 MiB |   85.14 MiB |    15.81% |
| Development dependency entries |          169 |          77 |    54.44% |
| Generated `dist/` directory    |  1,178,195 B | 1,166,645 B |     0.98% |
| Generated HTTP artifact        |  1,074,696 B | 1,063,146 B |     1.07% |

This is why the 0.8 split should be described as an install and packaging improvement, not as a dramatic reduction in the generated server itself. The production tree is about 90% smaller because build tools moved out of the runtime package; the self-contained HTTP artifact is roughly unchanged.

The SDK v2 migration also reduced duplicated runtime code. Against an untouched packed xmcp 0.8.0 baseline:

| Measure                          | 0.8.0 baseline | 0.8.1 candidate | Reduction |
| -------------------------------- | -------------: | --------------: | --------: |
| Runtime tarball                  |    2,018,611 B |     1,514,374 B |    24.98% |
| Total emitted runtime JavaScript |    5,580,784 B |     4,369,487 B |    21.70% |

Not every individual transport file became smaller—the new SDK implements more protocol behavior—but the adapter set shares substantially less duplicated code overall.

## Protocol support as tested

The [2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28) removes the required initialize handshake and protocol-level sessions. Requests carry their protocol revision, client identity, and capabilities in `_meta`; HTTP requests also use `Mcp-Method` and `Mcp-Name`. Multi Round-Trip Requests replace held-open server-to-client elicitation flows.

| Capability                                | Official SDK 2.0.0          | FastMCP 4.16.5 fixture                 | xmcp 0.8.1  |
| ----------------------------------------- | --------------------------- | -------------------------------------- | ----------- |
| Native MCP `2026-07-28`                   | Yes                         | Not demonstrated by the tested fixture | Yes         |
| 2025-era clients                          | Configurable legacy support | Yes                                    | Yes         |
| Stateless HTTP without protocol sessions  | Yes                         | Offers HTTP modes                      | Yes, always |
| `server/discover`                         | Yes                         | Tested request returned an error       | Yes         |
| `Mcp-Method` / `Mcp-Name` routing headers | Yes                         | Not demonstrated by the tested fixture | Yes         |
| Multi Round-Trip Requests                 | Yes                         | Not demonstrated by the tested fixture | Yes         |

The FastMCP package at 4.16.5 directly declares the v1 `@modelcontextprotocol/sdk` monolith. Its exact-pinned fixture successfully completed a 2025-era initialize request and returned an `Mcp-Session-Id`; the same fixture did not complete a direct 2026 `server/discover` request. This is a point-in-time test result, not a prediction about FastMCP's roadmap.

xmcp 0.8.1 uses the stable v2 server/client packages and keeps both client eras working. Modern requests use the 2026 envelope. Older requests go through the SDK's stateless fallback, which creates a fresh MCP server for every HTTP request. xmcp does not add a session cache or emit `Mcp-Session-Id`, and GET/DELETE session operations remain unavailable.

## Developer experience

Size is only one dimension.

### Official SDK

The official SDK is the reference implementation and the best choice when you want protocol-level control. You create a server, register each primitive, select a transport, and own the surrounding lifecycle. That explicitness is valuable for gateways, infrastructure, unusual transports, and learning the protocol.

The tradeoff is boilerplate. The runnable benchmark fixture needs both server and Node adapter packages plus its HTTP wiring.

### FastMCP

FastMCP offers an imperative framework API over MCP. You create a `FastMCP` instance, call `addTool`, and let the framework manage transport behavior and other conveniences. It is a natural fit if you prefer a central in-code registry and want more abstraction than the raw SDK.

Its npm tarball is the smallest of the three, while its tested production dependency tree and deployment footprint are the largest. Check its current Node and protocol compatibility against your deployment target.

### xmcp

xmcp's defining choice is file-based discovery. A file in `src/tools/`, `src/prompts/`, or `src/resources/` is the registration:

```typescript title="src/tools/greet.ts"
import { z } from "zod";
import type { InferSchema } from "xmcp";

export const schema = {
  name: z.string().describe("The name of the user to greet"),
};

export const metadata = {
  name: "greet",
  description: "Greet the user",
};

export default function greet({ name }: InferSchema<typeof schema>) {
  return `Hello, ${name}!`;
}
```

The framework supplies HTTP and STDIO transports, Express/Fastify/NestJS/Next.js adapters, Cloudflare Workers output, auth integrations, and self-contained builds. It keeps the existing Zod 3-or-4 contract while registering schemas through SDK v2's Standard Schema interface.

## How to choose

- Choose the **official SDK** when maximum control and the smallest normalized bundle matter more than framework conventions.
- Choose **FastMCP** when you want an imperative framework API and its feature set matches the protocol and Node versions you deploy.
- Choose **xmcp** when you want file-based discovery, built-in adapters and auth, strictly stateless dual-era HTTP, and a small self-contained deployment.

These projects solve different layers of the stack. Measure the artifact you actually deploy, verify the protocol revision your clients use, and pick the abstraction whose conventions fit your team.
