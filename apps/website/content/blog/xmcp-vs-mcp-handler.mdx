xmcp and mcp-handler can both expose MCP tools from an existing application. The main choice is how you want to organize and build those tools, rather than whether your server must be a separate service.

## Compare the integration model

| Concern              | xmcp                                 | mcp-handler                         |
| -------------------- | ------------------------------------ | ----------------------------------- |
| Organization         | Tool, resource, and prompt files     | Registration inside an HTTP handler |
| Existing application | Framework adapters                   | Fetch-compatible handler            |
| Standalone process   | HTTP and STDIO builds                | Application supplies the HTTP host  |
| Authentication       | Provider integrations and middleware | Bearer-token verification helpers   |

The current [mcp-handler documentation](https://github.com/vercel-labs/mcp-handler) describes v2, installed as `mcp-handler`. Its registration and transport options differ from v1; use the migration guide instead of old `@vercel/mcp-adapter` or SSE/Redis snippets.

## Choose xmcp for file-based organization

A tool can be a self-contained TypeScript file:

```typescript title="src/tools/greet.ts"
import { z } from "zod";
import type { InferSchema } from "xmcp";

export const schema = { name: z.string().describe("Name to greet") };
export const metadata = { name: "greet", description: "Greet someone by name" };

export default function greet({ name }: InferSchema<typeof schema>) {
  return `Hello, ${name}!`;
}
```

Use the [Next.js adapter](/docs/adapters/nextjs) when tools belong with your web application, or create a standalone project when it needs its own deployment. The same file-based workflow applies to resources and prompts.

## Choose around ownership and deployment

A request-handler approach fits teams that want MCP registration next to existing HTTP routing. File discovery fits teams that want separate modules for each capability and a compiler-managed build. In either case, keep authorization and business logic in code you can test independently.

Test an authenticated tool with your target client before choosing. Verify denied requests, input validation, and production hosting behavior. Neither framework removes the need to configure identity providers or protect access to your data.
