Don't paste an API key or personal access token (PAT) into an MCP config file as plain text. On the client, reference the secret from an environment variable or your OS keychain. For remote servers, prefer OAuth sign-in, so no long-lived token sits in the config at all. A config file that holds only references is safe to share. One that holds the real values is not.

On the server, keep secrets in the server's environment, never in tool output or logs. Use a different credential for clients calling your server than the one your server uses to call an upstream API, and never forward a client's token upstream. The MCP spec forbids that.

## Where should MCP credentials live?

| Credential                                | Store it in                                                              | Avoid                                      |
| ----------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------ |
| API key or PAT for a local (STDIO) server | Your shell environment or OS keychain, referenced from the client config | Literal values in a JSON config            |
| Key for a remote server you call          | Per-user OAuth, or a header that reads an env var                        | One shared key pasted into every laptop    |
| Upstream provider token used by a server  | The server's environment or secret manager                               | Client config, tool arguments, tool output |
| A user's token for a third-party API      | Your identity provider's token vault or exchange                         | Forwarding the MCP access token upstream   |

## How do I store an API key or PAT for a local MCP server?

A local server runs over STDIO, so it reads credentials from its environment. The [MCP authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) says STDIO implementations should "retrieve credentials from the environment" instead of using OAuth. Most clients pass that environment through an `env` block in their config. What differs is where the value comes from:

- **Claude Desktop extensions** let developers mark a setting as sensitive. Claude Desktop then encrypts it with the operating system's secure storage: Keychain on macOS, Credential Manager on Windows ([Claude Help Center](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)).
- **Cursor** resolves `${env:NAME}` in `command`, `args`, `env`, `url`, and `headers`, so the value stays in your shell environment ([Cursor docs](https://cursor.com/docs/mcp)).
- **VS Code** supports `inputs` with `"password": true` in the `.vscode/mcp.json` format. VS Code prompts for the value on first start and stores it securely ([VS Code docs](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)).
- **Claude Code** expands `${VAR}` in `.mcp.json` fields, including `env` and `headers` ([Claude Code docs](https://code.claude.com/docs/en/mcp)).

A Cursor entry that sends a key from your environment instead of the file:

```json title="~/.cursor/mcp.json"
{
  "mcpServers": {
    "billing": {
      "url": "https://mcp.example.com/mcp",
      "headers": {
        "x-api-key": "${env:BILLING_MCP_KEY}"
      }
    }
  }
}
```

Use the narrowest key the provider offers. Cursor's docs recommend "restricted API keys with minimal required permissions."

## Can I commit my MCP config file?

Only if it contains references, not values. Claude Code tells you to check a project `.mcp.json` into version control, which is fine when every secret is a `${VAR}`. VS Code's reference puts it bluntly: "Do not commit tokens, passwords, or populated authentication headers."

Personal config files leak too. In 2025, [Trail of Bits found](https://blog.trailofbits.com/2025/04/30/insecure-credential-storage-plagues-mcp/) MCP setups storing long-term API keys in plaintext files, some readable by any user on the machine. Treat a config with a pasted token like a `.env` file.

## Why is per-user OAuth better than a shared token?

A shared token makes every person the same caller. You can't revoke one person, your audit log can't tell them apart, and one leaked laptop exposes everyone. With per-user OAuth, each person adds only the server URL, signs in through the browser, and the client stores the resulting token. Nothing secret goes in the config.

[Roll out to a team](/docs/guides/roll-out-to-a-team) walks through this setup end to end. For how the OAuth flow works, see [MCP server authentication](/blog/mcp-server-authentication).

## How should an MCP server store its own secrets?

In the server's environment, loaded from a gitignored `.env` locally and from your host's secret settings in production. Projects created with `create-xmcp-app` already ignore `.env`. On Vercel, environment variables are encrypted at rest, and Secret values are write-only after saving ([Vercel docs](https://vercel.com/docs/environment-variables)).

Read the value inside the tool, not from a tool argument. Arguments come from the model, and anything the model sees can end up in a transcript.

## Should upstream credentials and client credentials be the same?

No. The server has two trust boundaries: clients calling your server, and your server calling a provider. Give each its own secret. The [X integration](/docs/integrations/x) uses `X_USER_ACCESS_TOKEN` for X and a separate `MCP_API_KEY` that clients send as `x-api-key`. Its middleware checks the client key before any tool runs:

```typescript title="src/middleware.ts"
import { apiKeyAuthMiddleware } from "xmcp";

export default apiKeyAuthMiddleware({
  validateApiKey: async (key) =>
    Boolean(process.env.MCP_API_KEY?.trim()) && key === process.env.MCP_API_KEY,
});
```

The tool then uses only the provider credential, and only toward the provider:

```typescript title="src/tools/list-invoices.ts"
import type { ToolMetadata } from "xmcp";

export const metadata: ToolMetadata = {
  name: "list-invoices",
  description: "List recent invoices from the billing API",
  annotations: { readOnlyHint: true },
};

function toolError(text: string) {
  return { isError: true as const, content: [{ type: "text" as const, text }] };
}

export default async function listInvoices() {
  const token = process.env.BILLING_API_TOKEN;
  if (!token?.trim()) return toolError("BILLING_API_TOKEN is not set.");

  const response = await fetch("https://billing.example.com/v1/invoices", {
    headers: { Authorization: `Bearer ${token}` },
    redirect: "error",
  });
  if (!response.ok) {
    return toolError(`Billing API returned HTTP ${response.status}.`);
  }
  return { structuredContent: await response.json() };
}
```

Leaking one secret now doesn't leak the other, and you can rotate them on different schedules.

## Can an MCP server forward the client's token to an upstream API?

No. The spec calls this token passthrough. Its [security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices#token-passthrough) state that "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." The authorization spec adds that servers "**MUST NOT** accept or transit any other tokens." The spec lists the risks: callers bypass controls tied to the token's audience, and neither your server nor the upstream API can tell who actually made the call.

When a tool must act as the user on a third-party API, get a separate token for that API. With xmcp, the [Auth0 plugin](/docs/integrations/auth0) can exchange the user's MCP token for one with a different audience. The [Descope plugin](/docs/integrations/descope) can fetch the user's stored token for a connected app with `fetchConnectionToken()`. If you store user tokens yourself, encrypt them and key them by the user ID from the verified token.

## How do tools get per-user credentials on stateless HTTP?

From the current request, every time. xmcp's HTTP transport is stateless, so an identity established in one request doesn't carry over to the next. Don't cache a user's token in server memory or a session. Validate the bearer token on each request and read the result inside the tool.

Auth plugins expose the verified user, for example `getSession().userId` with [Clerk](/docs/integrations/clerk). When an integration supplies SDK auth info, [`getRequestContext()`](/docs/core-concepts/request-context) exposes it as `authInfo`:

```typescript title="src/tools/whoami.ts"
import { getRequestContext, type ToolMetadata } from "xmcp";

export const metadata: ToolMetadata = {
  name: "whoami",
  description: "Show the client ID and scopes of the current caller",
};

export default async function whoami() {
  const { authInfo } = getRequestContext();
  return {
    structuredContent: {
      clientId: authInfo?.clientId ?? null,
      scopes: authInfo?.scopes ?? [],
    },
  };
}
```

The tool returns `clientId` and `scopes`, never `authInfo` itself. The request context docs warn that the object includes the access token.

## How do I keep secrets out of tool output and logs?

- Return only the fields the model needs. Never return headers, config objects, or `authInfo`.
- Don't pass raw upstream error bodies through. Return a status code and a short message, like the X example does.
- Don't log request headers or full auth objects. If you log a credential at all, log only an identifier you can rotate.
- Treat tool output as public. It goes to the model, the client's transcript, and anything else the client logs.

## How do I rotate MCP credentials?

Accept the old and new key for a short overlap, then remove the old one:

```typescript title="src/middleware.ts"
import { apiKeyAuthMiddleware } from "xmcp";

const acceptedKeys = [process.env.MCP_API_KEY, process.env.MCP_API_KEY_PREVIOUS]
  .map((key) => key?.trim())
  .filter((key): key is string => Boolean(key));

export default apiKeyAuthMiddleware({
  validateApiKey: async (key) => acceptedKeys.includes(key),
});
```

Set the new value as `MCP_API_KEY`, move the old one to `MCP_API_KEY_PREVIOUS`, redeploy, update clients, then delete the previous key. On Vercel, environment variable changes apply only to new deployments, so redeploy after each step. For upstream tokens, create the new token with the provider, update the server's environment, redeploy, then revoke the old one.

With per-user OAuth there is no shared client key to rotate. You remove one person's access in your identity provider without touching anyone else.
