An xmcp app needs a working MCP endpoint and a clear explanation of what its tools do before it is ready for directory review. This guide uses the [arcade project](https://github.com/xmcp-dev/arcade) and [Doom walkthrough](/blog/doom-with-xmcp) as examples. Start a new project with the [MCP app template](/templates/mcp-app).

## Use the current submission flow

OpenAI's submission process has changed since this article was first published. As of this review, the [official submission guide](https://developers.openai.com/plugins/deploy/submission) describes uploading a plugin ZIP, connecting its MCP server, resolving automated findings, and submitting a draft for review. Prepare the package using that guide rather than following the old ChatGPT Apps form.

Keep credentials out of the package. Supply review account details through the portal. Prepare positive and negative test cases, a walkthrough recording, and release notes. Follow the current asset requirements instead of relying on historical screenshot dimensions. Approval and publication are separate steps.

Check the [MCP review requirements](https://developers.openai.com/plugins/deploy/app-review) for endpoint availability, identity verification, authentication, and UI requirements. Review the current [plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines) for your use case, including any commerce functionality.

## Prepare your xmcp server

Deploy the server to a reachable HTTPS address and test it outside your development network. The [deployment docs](/docs/deployment/vercel) cover one supported path; the [integration catalog](/docs/integrations) covers authentication providers.

For domain verification, serve the portal's exact challenge token at `/.well-known/openai-apps-challenge`. xmcp standalone HTTP supports this through `OPENAI_APPS_VERIFICATION_TOKEN`. In adapter mode, implement the route in the host application and check the deployed response.

Make the tool metadata match the implementation. A description should explain its inputs, result, and side effects. Read-only, destructive, and open-world annotations describe different properties; calling a bounded private API does not by itself make a tool open-world. When you change annotations, deploy the server and rescan it before reviewing the imported values.

Use the [MCP apps metadata reference](/docs/core-concepts/mcp-apps) for widgets, including the domains they access. Test the text result as well as the rendered interface.

## Write reproducible test cases

For every test, record the starting state, user prompt, expected tool, and observable result. Use a review account with representative sample data. Do not assume a successful local demonstration proves the deployed endpoint behaves the same way.

For the arcade example, a positive case could be:

- Starting state: the arcade is connected and the game catalog is available.
- Prompt: “Show me the arcade games I can play.”
- Expected tool: `list_games`.
- Expected result: the catalog renders with working game selection controls.

A second case asks to launch Doom and checks that `launch_game` opens the selected game. A negative case asks a general historical question about Doom; the app should not launch a game merely because its name appears in the prompt.

Test failures too: an unavailable game, a failed upstream request, and an expired login should produce understandable results. Keep expected outcomes alongside your implementation so future tool changes can be checked against them.

## Review and maintain

Use the portal's current validation results to resolve submission issues. Keep a local copy of the package, metadata, release notes, and test cases. A directory listing does not replace monitoring your live server: authentication, external services, and deployed tool behavior can change after submission.
