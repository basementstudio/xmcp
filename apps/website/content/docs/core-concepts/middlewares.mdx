Define HTTP middleware with the default export of `src/middleware.ts`, and MCP middleware with its named `mcp` export. Both can live in the same file.

## HTTP middleware

HTTP middleware intercepts requests and responses, enabling authentication, rate limiting, and other processing tasks.

Create a `src/middleware.ts` file to define your middleware:

```typescript title="src/middleware.ts"
import { type Middleware } from "xmcp";

const middleware: Middleware = async (req, res, next) => {
  const authHeader = req.headers.authorization;

  if (!customHeaderValidation(authHeader)) {
    res.status(401).json({ error: "Invalid API key" });
    return;
  }

  return next();
};

export default middleware;
```

<Callout variant="info">
  xmcp provides built-in middlewares for common tasks like [API key
  authentication](/docs/authentication/api-key) and [JSON web token
  authentication](/docs/authentication/jwt).
</Callout>

## Chaining middlewares

Define multiple middlewares as an array to chain them in sequence:

```typescript title="src/middleware.ts"
import { type Middleware } from "xmcp";

const middleware: Middleware[] = [
  async (req, res, next) => {
    // First middleware
    return next();
  },
  async (req, res, next) => {
    // Second middleware
    return next();
  },
];

export default middleware;
```

## MCP middleware

Export one `McpMiddleware` function or an array as `mcp`. xmcp discovers it through the same `src/middleware.ts` file and applies it to tool calls, prompts, resource reads, completions, and listings over HTTP, STDIO, and the Node adapters. A default export is optional.

```typescript title="src/middleware.ts"
import { type McpMiddleware } from "xmcp";

const stampResult: McpMiddleware = async (ctx, next) => {
  if (ctx.method !== "tools/call") return next();
  const result = await next();
  return { ...result, _meta: { ...result._meta, tool: ctx.params.name } };
};

const checkName: McpMiddleware = (ctx, next) => {
  if (
    ctx.method === "tools/call" &&
    ctx.params.name === "greet" &&
    ctx.params.arguments.name === "blocked"
  ) {
    return {
      isError: true,
      content: [{ type: "text", text: "This name is blocked" }],
    };
  }
  return next();
};

export const mcp = [stampResult, checkName];
```

The first function enters first and receives the result last. `await next()` runs the remaining chain and the operation handler. Return a protocol result without calling `next()` to skip the remaining chain and handler. Call `next()` at most once; calling it twice rejects rather than executing the handler again. Return or await its promise so work stays inside the request lifecycle.

`ctx.method` identifies the operation and narrows `ctx.params`:

| Method                                                                     | Parameters                                               |
| -------------------------------------------------------------------------- | -------------------------------------------------------- |
| `tools/call`                                                               | `name` and SDK-validated `arguments`                     |
| `prompts/get`                                                              | `name` and optional `arguments`                          |
| `resources/read`                                                           | `uri`, for static, templated, and generated UI resources |
| `completion/complete`                                                      | `ref`, `argument`, and optional completion `context`     |
| `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list` | Optional pagination `cursor` and request metadata        |

Always check `ctx.method` before accessing operation-specific parameters. Existing middleware that assumes every request is a tool call should begin with `if (ctx.method !== "tools/call") return next();`.

`ctx` also includes `authInfo`, `clientInfo`, `http`, `signal`, `set`, `get`, `progress`, and `log` from [request context](/docs/core-concepts/request-context). `getRequestContext()` works before and after `next()`, and inside prompt, resource, and completion callbacks. Local values last for one operation and are isolated from concurrent requests. HTTP metadata is absent on STDIO.

Middleware receives normalized MCP results from `next()`. Return the result format for the current method; string and number shorthand belongs in component handlers. Check the result shape before accessing method-specific fields. Exceptions retain SDK behavior: tools produce tool-error results, while reads, prompts, completion, and listings reject with protocol errors. Invalid `mcp` exports or a failed middleware import prevent server setup from completing.

Tool middleware runs after the SDK resolves the tool and validates its input. Other methods are wrapped at SDK request-handler registration, before component lookup or callbacks. Resource template reads, template listing callbacks, and completion callbacks share that same chain and request scope. Only methods installed by the registered components are available. Initialization, ping, notifications, and unknown methods are unaffected.

Keep output-schema requirements intact when changing a tool result, and preserve interim `inputRequired` results when passing through multi-round tools.

### Registered tool metadata

After narrowing `ctx.method` to `"tools/call"`, `ctx.tool.metadata` is always available. Its exported type is `McpToolMetadata`: resolved `name` and `description`, optional `annotations`, `icons`, `tags`, and `_meta`. Defaults are applied, and `_meta` matches `tools/list`, including `"xmcp/tags"` and flattened UI keys such as `"ui/resourceUri"`. Resource-only UI settings are excluded. This is the registered view, not the tool module's original `ToolMetadata` export.

The metadata is a snapshot taken at registration. Plain objects and arrays are copied and frozen without freezing the original tool export or SDK configuration. Treat all metadata as read-only. `tool` is absent on other middleware methods and is not a field of `getRequestContext()`.

Use the same metadata policy to filter discovery and authorize direct calls:

```typescript title="src/middleware.ts"
import { type McpMiddleware, type RequestContext } from "xmcp";

function canCall(
  meta: Readonly<Record<string, unknown>> | undefined,
  authInfo: RequestContext["authInfo"]
): boolean {
  const required = meta?.["demo/requires"];
  if (required === undefined) return true;
  return (
    Array.isArray(required) &&
    required.every(
      (scope) => typeof scope === "string" && authInfo?.scopes.includes(scope)
    )
  );
}

export const mcp: McpMiddleware = async (ctx, next) => {
  if (
    ctx.method === "tools/call" &&
    !canCall(ctx.tool.metadata._meta, ctx.authInfo)
  ) {
    return { isError: true, content: [{ type: "text", text: "Forbidden" }] };
  }
  const result = await next();
  if (ctx.method === "tools/list" && Array.isArray(result.tools)) {
    return {
      ...result,
      tools: result.tools.filter((tool) => canCall(tool._meta, ctx.authInfo)),
    };
  }
  return result;
};
```

Declare `_meta: { "demo/requires": ["greet"] }` in the protected tool's metadata. Supply verified authentication through your HTTP integration; see [request-context authentication](/docs/core-concepts/request-context#authentication). Tools with no policy remain available, while malformed policies deny access. The [middleware array example](https://github.com/basementstudio/xmcp/tree/main/examples/middlewares-array) includes demo credentials and requests for both permitted and restricted callers.

### Filter discovery and deny direct access

Filtering a listing alone does not prevent clients from calling a known name or URI. Enforce the corresponding operation as well:

```typescript title="src/middleware.ts"
import { type McpMiddleware } from "xmcp";

export const mcp: McpMiddleware = async (ctx, next) => {
  if (
    ctx.method === "resources/read" &&
    new URL(ctx.params.uri).href === "demo://private"
  ) {
    throw new Error("This resource is private");
  }
  const result = await next();
  if (ctx.method === "resources/list" && Array.isArray(result.resources)) {
    return {
      ...result,
      resources: result.resources.filter(
        (resource) => resource.uri !== "demo://private"
      ),
    };
  }
  return result;
};
```

The same pattern applies to prompt and tool listings. Completion middleware can return `{ completion: { values: [] } }` without calling `next()` to suppress suggestions for a restricted prompt or resource reference.

The default HTTP export retains its existing transport behavior. STDIO loads the module to read `mcp` but does not invoke the default HTTP middleware. Keep module-level code safe to import on both transports.

For the Next.js adapter, keep the xmcp project separate from the Next.js application's source directory and import its compiled adapter into the route. Next.js reserves `src/middleware.ts` for its own request hook; placing xmcp's middleware there can make Next.js compile it as a Next.js hook. For example, use sibling `mcp/` and `web/` projects, with xmcp's file at `mcp/src/middleware.ts` and the Next.js route in `web/app/`.

See the runnable [middleware array example](https://github.com/basementstudio/xmcp/tree/main/examples/middlewares-array) for both exports together and curl requests that exercise each chain.

## Accessing headers

Use the `xmcp/headers` module to read request headers in your tools, prompts, or resources—useful for API keys, authentication tokens, and other custom headers.

```typescript title="src/tools/search.ts"
import { headers } from "xmcp/headers";

export default async function search({ query }: InferSchema<typeof schema>) {
  const requestHeaders = headers();
  const apiKey = requestHeaders["x-api-key"];

  const data = await fetchSomeData(apiKey);

  return JSON.stringify(data);
}
```
